## [Unreleased]

- Amended CR-OC-001C section 10.2 to use the token's default owner after the first hosted Windows CI run exposed a contract defect (documentation only): The pre-mutation ownership gate required the target's owner SID to equal the process token's `TokenUser`. That is the wrong quantity. `TokenUser` identifies the user account associated with the token, whereas `TokenOwner` is the default owner SID Windows applies to newly created objects when a process creates an object without supplying an explicit owner in a security descriptor. The gate's purpose is to establish that the temporary file this process is about to create will carry an owner compatible with the target, because `ReplaceFileW` documents preservation of the replaced file's DACL, timestamps, short name, object identifier, encryption, compression, and named streams but **not** its owner, and the resulting file retains the replacement file's identity — so the precondition must reason about the owner the new object will actually receive, which only `TokenOwner` answers. Section 10.2 now reads `GetTokenInformation(..., TokenOwner, ...)`, information class `4`, and a new section 10.2a records the discovery. The trigger was hosted run `30686689771`, the first execution of the `windows_executor` job against the implementation: NTFS verification passed, the mandatory executor group reported 131 passed and 34 failed, every one of the 34 failing uniformly at `metadata_precondition_failed`, and the structured-result gate correctly did not run after the mandatory failure. Every failure reached the ownership gate's closed refusal path before mutation, and because the implementation compared the target owner against `TokenUser` while `TokenOwner` governs the default owner of newly created objects, the hosted run exposed the contract defect — but the job did not disclose SID values and therefore does not establish the exact SID relationship on that runner, so a mismatch remains a strong explanation rather than an observed fact. Local Windows evidence had been green because the gate passed in the development environment; no persisted evidence established whether or why `TokenUser` and `TokenOwner` coincided there. The job's zero-skip, fail-closed design is what surfaced the defect rather than letting it pass quietly. The amendment is deliberately narrow about what it claims: it does **not** assert that hosted runners necessarily execute elevated, nor that the target's owner was any particular well-known SID, because those would be unverified explanations of *why* the two values differed and the contract defect does not depend on proving them — `TokenUser` was the wrong quantity for this precondition regardless of which specific SIDs a given machine reports. SID values are necessarily read into memory, since neither the gate nor `capture_security` can compare owners without them; what is forbidden is disclosure and persistence, so no raw SID is logged, serialized, persisted, placed in JUnit, included in the bounded job summary, or otherwise emitted, and tests may compare SID values in memory but report only equality or inequality. Section 17's exclusion of SIDs from results, projections, errors, JUnit, and the job summary is unchanged. Rather than adding a thirty-seventh obligation, T20 is revised into three parts — an injected incompatible default owner still refuses before mutation, a genuinely newly created file's owner equals the token's default owner, and an ordinary replacement passes the gate — so obligation totals stay at 36 while mutants move from 29 to 30. The new M30 defect is querying `TokenUser` instead of `TokenOwner`, and its killer is a deterministic instrumented assertion that the adapter requests information class `TokenOwner`, using a fake or instrumented `GetTokenInformation` so the kill does not depend on the two SIDs happening to differ on the machine under test — otherwise the mutant would survive on any host where they coincide, which is precisely how the defect escaped local evidence in the first place. This entry changes no code, tests, workflow, dependency, fixture, or configuration; the implementation on draft PR #128 remains unmerged and will be corrected after this amendment lands.

- Amended CR-OC-001C section 10.1 after an implementation-discovered contract defect (documentation only): The merged metadata invariant required strict equality of the `SE_DACL_AUTO_INHERITED` security-descriptor control bit across a replacement. Implementation against real Windows/NTFS found that a successful `ReplaceFileW` sets that bit on a file whose descriptor did not already carry it, while preserving every access-bearing component exactly — owner SID identical, three-valued DACL state identical, `SE_DACL_PRESENT` and `SE_DACL_PROTECTED` identical, ACL revision identical, ACE count identical, and all complete ACE byte sequences byte-identical including their `AceFlags`. The behaviour was systematic and one-directional: repeated replacements of the same file left the bit set and the ACEs byte-identical, a file already carrying the bit was stable in every component, and no observed transition ever cleared a bit or altered an ACE. As written the contract would therefore have reported `metadata_preservation_failed` for the first replacement of essentially any inherited-DACL repository file — an honest report of a mis-specified invariant rather than of a real access change — so the requirement was corrected before any test hardened it into permanent misleading behaviour. That bit is now governed by a monotonic rule recorded as section 10.1a: `False -> False`, `False -> True`, and `True -> True` are accepted and `True -> False` is rejected, with the `False -> True` exception valid **only** when owner SID, DACL three-state, presence, protection, ACL revision, ACE count, and ordered complete ACE bytes are all exactly preserved, so it can never excuse an ACE, ordering, revision, protection, presence, owner, or state difference. Complete exclusion of the bit was considered and rejected: Microsoft describes it as indicating that the DACL supports the automatic-inheritance model and Windows security APIs may set it when that model is applied, which makes it more than a disposable provenance marker even though it grants and denies no access by itself — unlike `SE_DACL_DEFAULTED`, which the section still excludes outright — and excluding it would additionally have accepted the opposite `True -> False` transition, which is broader than the evidence supports. The correction is recorded as an allowed normalization rather than a claim that Microsoft guarantees the behaviour on every version, edition, filesystem configuration, or ACL shape: `ReplaceFileW` is documented to preserve the replaced file's DACL, which it did, but its documentation does not promise byte-for-byte stability of every control flag, so the evidence generalizes only as far as "when this occurs alongside exact preservation of every access-bearing component, do not report a metadata failure." Hosted reproduction is deliberately observational rather than a merge gate, and review caught a contradiction in an earlier draft of this amendment that would have made it one: because the amended invariant accepts `False -> False`, `False -> True`, and `True -> True`, a hosted runner producing `False -> False` has exhibited another explicitly accepted transition rather than disproving anything, so requiring it to reproduce the normalization would have converted a single machine's observation into the very platform guarantee the amendment denies. The Windows job therefore starts from a confirmed pre-state, requires the observed transition to be one of the three accepted ones with every other owner/DACL component exactly preserved, records which transition it saw in the bounded job summary as two booleans and a bit name, and fails only on `True -> False` or another metadata difference; failing to reproduce `False -> True` is explicitly not a failure. The deterministic evidence for the rule is platform-neutral: both new tests construct snapshots directly and need no Windows, which is also why both new mutants are killed on Ubuntu — pointing the strict-equality mutant at the Windows half would have made its kill depend on which accepted transition a runner happened to exhibit, the same mutant-target-precision lesson CR-OC-001B recorded, applied before the evidence was collected rather than after. The evidence contract grows honestly rather than being held cosmetically at its previous totals: the test obligations move from 34 to 36 and the mutants from 27 to 29, adding a test that accepts `False -> True` only alongside exact preservation of every other component and rejects it per-component as soon as any one of them also differs, a test that rejects `True -> False`, a mutant that restores strict equality (the pre-amendment defect), and a mutant that ignores the bit entirely (the rejected complete-exclusion option). A pre-existing miscount in the merged implementation proposal is corrected in passing: the Ubuntu-killed mutant tally read "Seven" while listing eight, and now reads ten with the two additions. No code, tests, workflow, dependency, fixture, or configuration was changed by this amendment; the executor source files remain uncommitted while it is reviewed.

- Proposed CR-OC-001C (Constrained Single-File Replacement Executor): Recorded the requirements contract as a documentation-only proposal — revised once in draft after adversarial review, before any approval — for the mediated lane's one constrained filesystem effect: given an already constructed CR-OC-001A `AuthorizedContentEffect`, independently supplied exact proposed bytes, and a trusted mapping from `target_file_id` to one repository target, perform at most one single-file content replacement under explicit constraints and report the outcome through a closed vocabulary. The revision narrowed the platform decision from two mutating profiles to one: the executor is Windows/NTFS-specific over a platform-neutral pure core, because the drafted POSIX and Windows mutating paths shared almost nothing safety-bearing — different containment mechanism, replacement primitive, documented failure contract, metadata truth, and identity semantics — making them two executors under one name, with the POSIX half serving mainly to let Ubuntu-only CI stand in for evidence about the platform the lane actually targets; a stand-in is not evidence. Non-Windows platforms fail closed as `platform_unsupported`, Ubuntu CI exercises the pure core and the fail-closed gate only, and acceptance requires real Windows/NTFS evidence from either a separately approved Windows CI job — `.github/workflows/tests.yml` is a named allowlist candidate requiring explicit approval, never a silent addition — or a recorded local Windows run with commit, Python, and OS build captured. Windows claims no namespace atomicity, since Microsoft documents none for `MoveFileExW` or `ReplaceFileW`; `ReplaceFileW` through stdlib `ctypes` is selected for its documented DACL/attribute preservation list and per-error-code state contract, with `dwReplaceFlags` pinned to zero and a private random same-directory backup name always supplied because the documented no-backup failure mode deletes the replaced file. The backup lifecycle is fully specified: the backup is the original file object renamed by the primitive itself, carrying the original's own DACL; its name is unpredictable, collision-checked, and never disclosed in any result, projection, or error; it is deleted only after complete post-verification, with deletion failure reported as `backup_retained` on a still-verified outcome; it is retained deliberately on every ambiguous or failed outcome, in which states the executor performs no further filesystem operations at all; later invocations never scan for or clean abandoned artifacts; and recovery is exclusively human, gated on verifying the backup's bytes against `expected_pre_digest`. All three documented `ReplaceFileW` special errors are mapped by name in the closed classifier — `ERROR_UNABLE_TO_REMOVE_REPLACED` (1175) and `ERROR_UNABLE_TO_MOVE_REPLACEMENT` (1176) to `target_unchanged` strictly on Microsoft's documented name-retention statements for those codes, and `ERROR_UNABLE_TO_MOVE_REPLACEMENT_2` (1177), whose documented state can leave the target name absent, together with every undocumented failure, to `replacement_may_have_occurred` — and the classifier is required to be a pure, platform-neutrally testable function in which the 1175 mapping is asserted distinctly so it can never be flattened into the ambiguous 1177 outcome. The owner/DACL invariant is a structured comparison — semantic owner-SID equality; three-state DACL classification distinguishing absent, NULL, and present including the present-empty DACL; the pinned control bits; ACL revision and ACE count; and ordered complete per-ACE byte-sequence equality, with every `ACE_HEADER.AceSize` validated against the containing ACL's bounds before use, unknown ACE types compared as complete opaque byte sequences rather than partially parsed or ignored, malformed structures failing closed, and slack space outside the enumerated ACEs excluded — never a field tuple, which would omit object-ACE GUIDs, callback/conditional application data, and inheritance payload, and never raw SDDL string equality, which no authority documents as canonical. SACL, primary group, and provenance-only bits are excluded for stated reasons, and owner preservation is made satisfiable by a pre-mutation gate requiring the target's owner to equal the executing principal. The identity claims are corrected to what handles actually prove: a validation handle validates the original object only and constrains nothing about how `ReplaceFileW` independently resolves the target name, so the handle is closed after capture, an immediately-prior identity re-probe narrows but cannot close the swap window, the no-concurrent-external-writer assumption is explicitly load-bearing across the unclosable interval, and post-verification re-resolves entirely through the frozen registry because the post-replacement object legitimately carries a new identity. Observing the postcondition is stated not to prove that this invocation performed the replacement; `replacement_verified` asserts the conjunction of the single primitive call succeeding and the postcondition being observed afterward. Degenerate `pre == post` effects are rejected as a scope and API rule: the operation this executor defines is an actual content transition, equal digests describe no such transition, the rejection is explicitly not replay prevention — duplicate-request authority remains CR-OC-001B's alone — and observing that the file already holds the expected bytes would not prove this invocation caused that state; a future separately scoped observational operation could define an `already_at_authorized_postcondition` result, which this executor does not implement. No automatic rollback exists on any path, including from the backup: restoring pre-content would be a second mutation without a fresh guard. Resolution, containment, evidence, concurrency, and API constraints carry over from the first draft: `target_file_id` is the sole resolution key against a frozen operator-constructed registry, `canonical_relpath` is byte-compared evidence that never resolves anything, containment is reparse rejection plus final-path verification of the actually opened handle with no lexical prefix check anywhere, cross-process exclusion and hostile-process resistance are explicitly not claimed, and the API accepts only the registry, the effect, and immutable `bytes`. Thirty-four test-contract items tagged neutral-versus-Windows and twenty-seven designated mutants are named before any code exists — including mutants that omit object-type GUID data, omit callback application data, regress to a type/mask/SID tuple, ignore ACE order, accept a malformed `AceSize`, and flatten the 1175 error into the ambiguous class, each with a designated killer — the unkillable equality-preserving resolution variant is recorded as reviewer-controlled, and the POSIX access-control lesson — mode bits do not establish ACL preservation where extended ACLs exist — is recorded for any future POSIX addendum. The provisional implementation allowlist remains `triage_core/mediated_executor.py`, `tests/test_mediated_executor.py`, and the three documentation paths. This entry grants no implementation or execution authority; no code, tests, schema, CLI, CI, runtime integration, IPC, file access, dependency, OpenClaw installation, or capability or reservation behavior was changed.

- Implemented CR-OC-001B (Atomic Client-Request Reservation): Added `triage_core/request_reservation.py`, a versioned local SQLite store binding one client request to at most one capability. The database enforces the invariants rather than the Python caller: `client_request_id` primary key, a partial unique index on `capability_id`, a table-level `CHECK` binding row shape to each state, and triggers for immutable request identity, the legal transition whitelist (`reserved -> issuing`, `reserved -> denied`, `issuing -> authorized` and nothing else), immutability of a bound capability, and undeletability. Every transition out of `reserved` or `issuing` performs one atomic conditional write under `BEGIN IMMEDIATE` whose predicate carries the client request, the required current state, and the attempt verifier, requiring exactly one changed row. The ownership token is generated with 256 bits of OS-backed randomness, returned raw exactly once to the insert winner, and persisted only as `sha256(token)`; the raw value never enters SQLite, projections, evidence, logs, or error payloads, and the stored verifier is never accepted as a substitute. The one-shot `reserved -> issuing` gate is consumed before `issue_capability` is called, because a one-to-one constraint on binding does not bound how many capabilities exist. The mediated issuance path verifies the effect, request, and linkage through the CR-OC-001A helpers and checks that the authorization receipt's task, decision, artifact, scope, and plan bindings describe that exact trio before the gate is taken; if issuance raises or binding cannot complete, the row stays permanently `issuing` and never returns to `reserved`, permits denial, or authorizes a second issuance. The mediated claim path delegates to the existing claim API only for an authorized reservation and explicitly does not alter or constrain direct callers of `triage_core.authz.claim_capability`. Tests cover all 16 named obligations with real threads over independent connections and direct-SQL proof of every schema-level invariant. Two evidence defects are recorded rather than smoothed over: the connection-mismatch test initially passed with the connection comparison deleted, because `broker_connection_id` is inside the request digest, and was only exposed when that mutant survived — it now observes a directly seeded row whose digest matches while the connection differs; and two mutants were killing at collection with a syntax error rather than a missing constraint, so the harness now removes whole SQL tuple elements and treats a collection error as not a clean kill. A review round then closed five further defects: the issuance gate now carries the request digest and broker connection in its atomic predicate, because a valid token for one reservation could otherwise advance it while a capability was issued for a coherent different request sharing the client request id and bound into the first reservation's row; a decision-bearing lookup distinguishes absence from busy and unavailable so the mediated claim path can no longer report a locked or corrupt store as though no reservation existed; a state-aware classifier replaces one generic wrong-state code per operation, so a denied row reports denial rather than already-issuing and rebinding the same capability recovers the existing binding rather than claiming issuance never began; the exact persisted row payload is checked against the privacy invariant before insertion rather than only its later projection; and the concurrency helpers capture worker exceptions, bound their joins, and assert the result count so a crashed worker fails the test instead of silently shrinking the evidence. A third round narrowed two remaining reason-code claims: every insert `IntegrityError` had reported `reservation_unbound`, asserting a valid reservation exists that this caller merely does not own, when `BEGIN IMMEDIATE` already serialises conforming writers so the error can equally indicate an incompatible trigger or unexpected constraint — only a `client_request_id` uniqueness conflict now re-reads and classifies the actual row, and anything else reports `reservation_store_unavailable`; and a locked-store test that accepted either busy or unavailable now requires exactly `reservation_store_busy`. A fourth round added installed-schema validation, since `PRAGMA integrity_check` proves SQLite's own structures are consistent rather than that the application's constraints exist and `CREATE TABLE IF NOT EXISTS` cannot retrofit a table-level `CHECK` or `PRIMARY KEY`: the store now compares the normalized DDL of the table, index, and all four triggers against its canonical definitions before use, because presence alone would accept an altered trigger that enforces nothing. The same round moved the mediated claim's request-identity comparison ahead of its state check, so a coherent request sharing another's client request id is told it is not the reserved request rather than whatever that reservation happens to be doing. Twelve required mutants plus six review-found variants, eighteen exercised in total, were each demonstrated failing against their defective versions. No runtime module imports the store, no new dependency is added, and `authz.py`, `capability_claims.py`, `task_ledger.py`, and `mediated_effect.py` are unmodified.

- Proposed CR-OC-001B (Atomic Client-Request Reservation): Recorded the requirements contract as a documentation-only proposal for the durable binding CR-OC-001A cannot provide — `client_request_id` to `request_digest` to `broker_connection_id` to `capability_id` — so two callers cannot obtain authority for the same logical operation. The proposal answers the ordering question explicitly: reservation precedes capability issuance, because issuing first would leave a crash window in which a capability exists with no reservation recording which client request owns it, whereas reserving first leaves an inert reservation instead. It also refuses to hide the remaining window: capability issuance appends to the JSONL ledger while the reservation lives in SQLite, so no single transaction spans both, and a durable ownership token handed once to the insert winner decides who may advance the row — returned raw exactly once and persisted only as `sha256(token)`, since storing a bearer credential raw would hand the right to bind or deny any live row to anyone who can read the database — so a retry may inspect a reservation but never receives the token and a lost owner leaves it inert by construction — avoiding both failure modes of an unowned row, where a retry either sabotages a live in-flight issuer or lets a stranger perform the bind the crashed invocation owned. The reason code is `reservation_unbound` rather than anything asserting a crash, because no caller can distinguish a crashed invocation from a live one. A one-shot `reserved -> issuing` transition consumes the right to issue before `issue_capability` is called, because two invocations holding the same valid token could otherwise both issue capabilities and only then race to bind: the uniqueness constraint would permit one binding while the second capability already existed in the ledger and stayed claimable through the unchanged direct claim path. The lifecycle deliberately stops at `reserved -> issuing -> authorized`, with `reserved -> denied` as the only other transition and denial illegal once issuance has begun; continuing into claimed and terminal states would create a second lifecycle authority mirroring CR-YK-002 across two stores with no shared transaction and no defined reconciliation, so claim and execution lifecycle stay exclusively in CR-YK-002. Reservation gating is scoped to the CR-OC mediated entry point rather than claimed globally: `issue_capability` mints the capability ID internally and appends issuance to the JSONL ledger, and `claim_capability` locates that issuance and delegates straight to the claim store with no reservation lookup, so a new wrapper can refuse to delegate but cannot make the existing public API incapable of claiming, and making reservation authorization a prerequisite for all claiming would be a materially larger authority change requiring its own proposal. One-to-one binding is enforced by schema uniqueness in both directions and proven by direct-SQL tests, following the v2 claim-store pattern rather than repeating its v1 mistake of documenting an invariant the schema did not enforce. Capability expiry must not release a reservation, since that would make expiry a reuse channel a caller could simply wait out. Store failure is distinguished from a successful lookup finding no row, carrying the CR-YK-002 terminal-reason correction forward before the defect can be written rather than after. Binding verifies that effect, request, and linkage describe one transition, because CR-OC-001A shipped a transplant defect proving that individually valid component digests are not evidence that the components belong together. The connection binding is currently subsumed by the request digest and must therefore be tested independently, so that removing `broker_connection_id` from the digest object cannot silently legalise cross-connection reuse. Sixteen tests and twelve mutants are named before any code exists. The acceptance claim is bounded to atomic reservation and at-most-once capability binding, and explicitly does not extend to broker authenticity, request provenance, file protection, OpenClaw containment, or execution safety.
